# Single-Line Pipeline Reading Guide

The best way to understand this repository is to follow the path of one image through the system. The service is a Google Cloud Pub/Sub consumer: it waits for a message that describes an image in GCS, downloads that image, runs the single-line SKU pipeline, and publishes a normalized SKU result for downstream systems. Start in `app.py`, because that file shows the production control flow. The method `streaming()` creates the Pub/Sub subscriber, and each incoming message is passed into `process()`. From there, `process()` parses the message, downloads the image, calls the new inference pipeline through `process_image_new()`, and falls back to the older full-image OCR path through `process_image()` if the new pipeline does not produce usable SKUs.

After `app.py`, the most important file is `new_inference_pipeline_full_image.py`. The central method is `HomeDepotInferencePipeline.run_image()`. This method is the single-line computer vision pipeline itself. It first sends the full image to the object detection model, which detects candidate single-line label regions such as `Pallet`, `RDC`, `Printed_on_Box`, and `Handwritten`. The pipeline intentionally skips `Multiline_Label` because multiline labels belong to a different pipeline. Each detection is buffered, cropped from the original image, lightly preprocessed, and stored with tracking metadata in a `ClipTrack` object.

The next important concept is strip creation. Detected label crops can have different sizes, so `create_strip()` groups a small number of crops, pads them to a common size, and concatenates them horizontally into a strip image. This matters because the segmentation model was trained to operate on these crop strips. While building the strip, the pipeline records exactly where each crop lives inside the strip, including padding offsets and crop boundaries. That bookkeeping is essential because later the code needs to map segmentation and OCR results back to the original full image.

Once strips are built, `_mask_single_strip()` runs the segmentation model to find the actual SKU digit region inside each detected label crop. If segmentation succeeds, only the SKU-text region is kept. If segmentation fails for a crop, the code preserves the full crop instead of discarding it. This is a practical fallback: a weak segmentation result should not completely prevent OCR from seeing a label that object detection already found.

The most important OCR improvement happens in `_build_masked_original_image()`. Instead of sending the original noisy shelf image directly to Google OCR, the pipeline creates a new full-resolution image where only the likely SKU regions are visible. Everything else is replaced with a configurable background, usually white. This reduces visual noise while preserving original image coordinates, which means Google OCR results can be interpreted directly in the original image space. The parameters `background_mode`, `mask_roi_pad_px`, and `small_label_area_threshold` control how aggressive this masking is.

After the masked original image is created, `_run_google_ocr_words()` calls Google OCR and passes the OCR annotations into `utils/google_ocr_utils.py`. That file is where OCR text becomes structured SKU candidates. The key function to understand is `parse_google_ocr_words()`, supported by helpers such as `normalize_sku_candidate()` and `bbox_from_google_annotation()`. The SKU rules are intentionally strict: useful SKUs are generally 6 or 10 digits, sometimes with spaces, hyphens, prefixes, or OCR noise that must be normalized carefully.

Once OCR words are parsed, `_assign_word_to_track_in_original()` connects each OCR result back to the detection it came from. It first checks whether the OCR word center falls inside a buffered detection box, then falls back to overlap matching if needed. This is how the final output can say not only which SKU was found, but also which detected label class and original image region produced that SKU.

To understand the model boundary, read `services/image_inference.py` after the pipeline file. The class `VertexModelInferenceService` wraps the calls to Home Depot's Vertex AI private endpoints. `predict_detection()` calls the object detection endpoint and `parse_detection_outputs()` converts the raw response into `BoundingBox` objects. `predict_segmentation()` calls the segmentation endpoint and `parse_segmentation_outputs()` converts the raw response into a binary mask. This file explains what the production service expects the deployed models to return.

The shared data structures live in `common_config.py`. Read `BoundingBox`, `ClipTrack`, `OCRWordResult`, and `PipelineResult`. These classes are small, but they are the vocabulary of the system. `BoundingBox` represents locations in image space, `ClipTrack` follows one detected label through crop, strip, segmentation, and OCR assignment, `OCRWordResult` represents a final parsed OCR result, and `PipelineResult` is what the inference pipeline returns to `app.py`.

The older SKU parsing logic is in `translators/atomic/entity_translators.py`. This file is useful because it shows the legacy regex assumptions around SKU formats and vendor SKUs. Even though the new pipeline uses `utils/google_ocr_utils.py` for OCR parsing, both paths are solving the same core problem: turning noisy OCR text into reliable 6-digit or 10-digit SKU values.

Finally, use `test/test_app.py` as executable documentation. The tests show how OCR fixtures are passed into SKU extraction, how bounding boxes are detected, and how the final published JSON payload is constructed. Since the real detection and segmentation endpoints require private access, these tests are the fastest local way to understand the service behavior without VPN.

In short, read the repository in this order: `app.py` for the service lifecycle, `new_inference_pipeline_full_image.py` for the image pipeline, `services/image_inference.py` for model calls, `common_config.py` for shared objects, `utils/google_ocr_utils.py` for OCR parsing, `translators/atomic/entity_translators.py` for legacy SKU rules, and `test/test_app.py` for runnable examples. If you understand how one image moves through those files, you understand the single-line pipeline.
