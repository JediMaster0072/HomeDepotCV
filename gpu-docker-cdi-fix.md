# GPU Docker Runtime Fix — RTX 5090 Host (172.16.20.108)

**Date:** July 6–7, 2026
**Host:** `GPU5-A5090` (172.16.20.108) — 2x NVIDIA RTX 5090, driver 595.71.05, CUDA 13.2
**Status:** ✅ Resolved and confirmed durable across reboot

---

## Summary

Docker containers on this host could not access the GPUs via `--gpus all`, even though the host itself could see both RTX 5090s fine via `nvidia-smi`. This forced all inference workloads into CPU-only mode. The root cause was a path-resolution mismatch inside Docker's Snap confinement, and it's now fixed with a systemd unit that regenerates and patches the NVIDIA CDI spec on every boot, before Docker starts.

---

## The problem

- The host runs Docker as a **Snap package**, which runs services (dockerd, containerd) inside a confined mount namespace.
- GPU passthrough into containers uses NVIDIA's **CDI (Container Device Interface)** spec, a YAML file at `/var/run/cdi/nvidia.yaml` that lists every device, library, and binary a GPU container needs, and where to find it on the host.
- This spec is generated by the `nvidia-container-toolkit` (packaged as a component of the docker snap: `snap.docker.nvidia-container-toolkit.service`).
- The generated spec listed some `hostPath` (mount) and hook `path` entries as **bare host paths**, e.g.:
  ```yaml
  hostPath: /usr/bin/nvidia-cuda-mps-control
  ```
- Problem: from *inside* the docker snap's confined mount namespace, `/usr/bin/...` does **not** point to the real host filesystem. Only paths prefixed with `/var/lib/snapd/hostfs/` reach the real host from inside that confinement — this was confirmed directly with `snap run --shell docker -c "ls /var/lib/snapd/hostfs/usr/bin/nvidia-cuda-mps-control"`, which succeeded, while a plain `ls /usr/bin/nvidia-cuda-mps-control` from inside a launched container failed.
- Result: any GPU container that needed CUDA MPS control/server binaries (which is essentially any real GPU workload) failed at container-creation time with errors like:
  ```
  failed to fulfil mount request: open /usr/bin/nvidia-cuda-mps-control: no such file or directory
  ```
  or, for hook paths:
  ```
  error running createContainer hook #0: fork/exec /usr/bin/nvidia-cdi-hook: no such file or directory
  ```

### Why this was hard to pin down
- Some entries in the generated spec already had the correct `hostfs` prefix and worked fine — only ~26–28 of ~52 `hostPath`/hook entries were bare, likely a toolkit quirk in how it resolves paths for different binary/library categories.
- The spec is regenerated fresh each time `nvidia-container-toolkit` runs, and is stored under `/var/run`, which is tmpfs and wiped on every reboot — so any manual fix (like a one-off copy or hand-edit) does not survive a restart.
- An earlier, incorrect workaround copied a **static bundled template** from `/var/snap/docker/<rev>/etc/cdi/nvidia.yaml` over the live spec. This happened to work once by coincidence but is not the actual generated spec and does not reflect the real installed hardware/paths — it was replaced with the correct fix below.

---

## The fix

A script and a systemd unit that run automatically before Docker starts, on every boot.

### 1. `/usr/local/sbin/fix-nvidia-cdi.sh`

```bash
#!/bin/bash
set -euo pipefail
DST="/var/run/cdi/nvidia.yaml"
mkdir -p "$(dirname "$DST")"

# Run the real generator: inspects attached GPUs and writes a fresh,
# hardware-accurate CDI spec directly to $DST.
systemctl start snap.docker.nvidia-container-toolkit.service || true

# Wait for it to actually produce the file (it's a oneshot; give it time).
for i in $(seq 1 30); do
  [ -f "$DST" ] && break
  sleep 1
done

if [ ! -f "$DST" ]; then
  logger "fix-nvidia-cdi: ERROR $DST was not generated by the toolkit service"
  echo "ERROR: $DST not generated" >&2
  exit 1
fi

cp "$DST" "${DST}.bak.$(date +%s)" 2>/dev/null || true

# Patch snap confinement path mismatch: bare /usr and /run paths (both
# mount hostPath entries and hook "path:" entries) aren't reachable from
# inside the docker snap's confined mount namespace -- only the
# /var/lib/snapd/hostfs-prefixed equivalents are.
sed -i -E "s#^([[:space:]]*- hostPath: )(/usr/|/run/)#\1/var/lib/snapd/hostfs\2#" "$DST"
sed -i -E "s#^([[:space:]]+path: )(/usr/|/run/)#\1/var/lib/snapd/hostfs\2#" "$DST"

logger "fix-nvidia-cdi: regenerated and patched $DST"
```

### 2. `/etc/systemd/system/fix-nvidia-cdi.service`

```ini
[Unit]
Description=Regenerate and patch NVIDIA CDI spec before Docker starts
DefaultDependencies=no
After=local-fs.target snapd.service
Before=docker.service snap.docker.dockerd.service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/fix-nvidia-cdi.sh
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
```

Enabled with:
```bash
sudo systemctl daemon-reload
sudo systemctl enable fix-nvidia-cdi.service
```

### What the fix does NOT touch
- `/dev/nvidia*`, `/dev/dri/*` device node paths — these resolve fine unprefixed since `/dev` is shared across the snap confinement boundary.
- `/lib/firmware/nvidia/.../*.bin` paths — confirmed to resolve identically with or without the `hostfs` prefix, so left as-is.

## Verification performed

1. Ran the script manually — confirmed it regenerates a full 52-`hostPath`-entry spec and correctly patches all bare `/usr/`/`/run/` paths (2 firmware paths intentionally left unprefixed).


   → Both RTX 5090s visible cleanly inside the container.
3. **Full reboot test** (the real durability test):
   - Confirmed no active containers/work on the host first (`docker ps` empty).
   - Rebooted the host.
   - After boot, confirmed `fix-nvidia-cdi.service` → `active (exited)`, success, with no manual intervention.
   - Confirmed the regenerated spec had 50/52 entries correctly `hostfs`-prefixed (2 firmware entries intentionally unprefixed, as expected).
   - Re-ran the `--gpus all` smoke test → both RTX 5090s visible, no errors.

**Result: the fix is durable and requires no manual steps after any future reboot.**

## Known side notes / minor follow-ups (non-blocking)

- `snap.docker.nvidia-container-toolkit.service` is a oneshot service that is not "always running" — it's meant to be triggered, which our new unit now does automatically at boot. This is expected/correct behavior, not a bug.
- dockerd logs show a repeating error (`No such container` on an `/attach` call, plus several `docker-proxy` processes bound to ports 8050/8501/8888 pointing at a container that appears to no longer exist). This looks like leftover state from a container Docker's restart policy is trying to reconnect to. Not blocking GPU access, but worth a `docker ps -a` / cleanup pass when convenient.
- A reboot during this investigation killed two containers that were running at the time (`hd-det-current-cpu`, `hd-det-current-cpu-weights`, both CPU-mode test containers, up 42+ minutes). No other active sessions or GPU processes were found running at the time. Always check `docker ps` (and confirm with any other users of the host) before rebooting a shared GPU box in the future.

- Inference no longer needs to fall back to CPU-only mode.
